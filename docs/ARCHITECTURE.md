# ReadAloud Enhancer architecture v0.1

Documentation date: 2026-11-11. Application baseline: v0.12.

## Evidence and scope

This document summarizes the supplied Technical Handoff v0.1 (2026-11-11) and the v0.12 release documentation. The handoff reports inspection of the original C# source on the Windows development host. That source is not yet present in this repository or the supplied deployment archive; implementation details below have not been independently rechecked against C# in this documentation update.

ReadAloud Enhancer captures audio already generated by ChatGPT, preserves it locally, and provides independent local playback. It does not generate speech through a second TTS engine or require a paid API.

## Capture and publication

Engine scans desktop cache candidates on a background task. Recognized complete audio frames are appended to Enhancer-owned archive files. HistoryStore.Capture updates the recording metadata and saves the index after the append. The saved index is the committed-byte boundary: physical file growth alone does not establish publication.

Engine exports a snapshot of captured audio. Engine.FinishExport publishes the resulting MP3 and updates its index. A growing recording may receive progressively longer MP3 revisions. Snapshot playback ending does not establish that the entire ChatGPT utterance has been captured.

The handoff describes AAC-LC ADTS and a restricted MPEG-2 Layer III parser; sampled recordings were 24 kHz mono. These observations are not a guarantee that all future recordings have that format.

## Threading and playback

Engine serializes archive mutations and scan work in a background task and dispatches commands through a queue. UI updates are marshalled to the UI thread. Playback preparation and conversion run in background work; UI Automation has a separate worker.

Local playback uses snapshots. Watch observes new/updated candidates; Watch and Play also queues playback. Stop holds the local queue. Capturing and archiving can continue independently of the local player.

v0.12 persists the selected observation mode, but not the pending playback queue. Restoring Watch and Play does not enqueue the entire old archive.

## Bridge boundary

ReadAloud Bridge is planned, not implemented by this documentation update. Its publisher should run independently of the scan/UI threads, read only committed data, and coordinate reads with retention and revision replacement. Android and Windows clients must own their individual playheads, decoders, queues and volume.

The Integration Server's existing fixed PCM transport remains a separate capability. See [Bridge roadmap](BRIDGE-ROADMAP.md).
